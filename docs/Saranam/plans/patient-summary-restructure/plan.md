# Patient Summary Restructure + Test Patient Seed

**Date:** 2026-05-14
**Status:** Plan — approved, not yet implemented
**Owner:** Saranam team

## Why

The current AI Patient Summary card emits a single free-form paragraph generated by Gemini covering everything — demographics, scores, narrative. Two problems:

1. The AI is asked to render data that the database already holds verbatim (name, age, sex, UHID, address, ESAS/PPS numbers). That wastes tokens, risks hallucination, and produces prose where a clinician wants a quick-scan chart.
2. There is no self-contained way to spin up a fully-populated test patient for QA or client demos. `seed_faisal_test.py` requires the patient row to already exist.

Goal: turn the card into a **clinician quick-view** — deterministic fields rendered from the DB, narrative blocks AI-summarised from the assessment forms — and provide a one-command seed for a realistic test patient with full baseline data.

## Target layout (from client spec)

```
Basic Patient Details      ← DB, deterministic
  Name, UHID, Homecare ID, Age/Sex, Address, Phone,
  Primary Caregiver, Date of Registration

Clinical Details
  Diagnosis                ← verbatim from doctor.diagnosis

Present Complaints         ← verbatim from doctor.chief_complaints

Functional Assessment
  ESAS                     ← raw scores from EsasScore (table)
  Performance Status (PPS) ← raw scores from PpsScore (table)

Nursing Assessment         ← AI-summarised
Psychosocial Assessment
  Psychological Distress   ← AI-summarised (distress score deterministic)
Physiotherapy Assessment   ← AI-summarised

Homecare Visit Details     ← deterministic table from PatientVisit + PlanOfCare
  Date | Team Members | Findings | Interventions | Plan of care

Follow-up visit summary    ← existing per-visit summaries
```

## Decisions (locked in 2026-05-14)

- **Diagnosis & Present Complaints**: copy verbatim from doctor form. No AI.
- **Regenerate behavior**: one confirm dialog if any AI block has been edited; then overwrite all.
- **Test patient profile**: realistic Bangalore-based Indian patient, plausible demographics, full baseline assessments, idempotent on UHID.

## Part A — Structured Patient Summary

### A1. Prompt rewrite

File: `backend/app/ai/assessment_summary_prompts.py`

- Replace `PATIENT_COMBINED_STRUCTURED_SYSTEM` with a JSON-schema prompt that returns:
  ```json
  {
    "nursing": "≤120 word clinical paragraph",
    "psychosocial": "≤120 word clinical paragraph",
    "physiotherapy": "≤120 word clinical paragraph",
    "body_locations": [...]
  }
  ```
- Drop demographics, age, sex, ESAS numbers, PPS numbers, address, diagnosis, chief_complaints from the prompt context. Pass only the three assessment record bodies + previous body locations.
- Keep existing rules (only present fields, never invent, "Insufficient data recorded" fallback per block).
- Drop `PATIENT_COMBINED_SYSTEM` (legacy non-structured) — no remaining callers after this change.

### A2. Generator + route

Files: `backend/app/ai/assessment_summary.py`, `backend/app/saranam/routes/patient_summary.py`

- `summarize_patient()` now returns `{ blocks: {nursing, psychosocial, physiotherapy}, body_locations: [...], model: "..." }`.
- `POST /saranam/patients/<id>/summary/generate` returns that shape (plus `diff_stats` as today).
- `PUT /saranam/patients/<id>/summary` accepts `{ summary_blocks: {...}, body_locations: [...], model }`.

### A3. Storage

File: `backend/app/saranam/models/patient_ai_summary.py` + new Alembic migration.

- Add `summary_blocks` JSONB column (nullable).
- Keep `summary_text` column populated with a flattened concatenation of the blocks (joined by `\n\n`) as a back-compat fallback for any consumer that still reads it.
- Migration: `backend/migrations/versions/<rev>_patient_summary_blocks.py` — add column, no backfill (existing rows keep `summary_text`, `summary_blocks` stays NULL until next Generate).

### A4. Frontend card

File: `frontend/src/components/patients/AiPatientSummaryCard.jsx` (likely a partial rewrite — the card grows from one textarea to several sections).

Sections, in order:

1. **Basic Patient Details** — read-only grid from `patient` prop. Age computed from `date_of_birth`. Address/contact use existing decrypt helpers used elsewhere on the profile.
2. **Clinical Details / Diagnosis** — read-only text from latest `DoctorAssessment.diagnosis` (initial visit). Show "—" if blank.
3. **Present Complaints** — read-only from latest `DoctorAssessment.chief_complaints`.
4. **Functional Assessment** — small ESAS table (9 symptoms, latest scores) + PPS row. Sourced from `EsasScore` + `PpsScore` latest-per-patient, not AI.
5. **Nursing / Psychosocial / Physiotherapy** — three editable `<TextField multiline>` blocks bound to `summary_blocks.{nursing,psychosocial,physiotherapy}`. Each shows "Last generated <time>" badge.
6. **Homecare Visit Details** — table of all `PatientVisit` rows for this patient (date, team_members, visit_summary, linked PlanOfCare intervention summary).
7. **Follow-up visit summary** — existing per-visit list (no change to that subsystem).

Top controls unchanged: Generate, Save, Download PDF. Generate dispatches a confirm dialog if any of the three AI blocks differs from the last-saved `summary_blocks`.

Data fetching: card needs `DoctorAssessment` (initial), `EsasScore` (latest), `PpsScore` (latest), `PatientVisit[]`, `PlanOfCare[]`. Most are already fetched on the Overview tab; check what's available via props before adding new API calls.

### A5. PDF

File: `frontend/src/utils/generatePatientSummaryPDF.js`

- Rewrite layout to mirror the new card: section headings, two-column grid for Basic Details, tabular ESAS/PPS/Visits, the three narrative blocks.
- Keep the existing jsPDF dependency.

### A6. API client

File: `frontend/src/api/saranam.js`

- `generatePatientSummary` and `savePatientSummary` shapes change to `summary_blocks`. Update accordingly.

## Part B — Test patient seed

New file: `backend/seed_test_patient.py`

- Use `create_app('development')` + `db.session`.
- **Idempotent on UHID** `SARANAM-TEST-0001`:
  - Find-or-create the `Patient` row with realistic Bangalore demographics:
    - Name: realistic Indian name (e.g., "Rajesh Kumar")

    - Address (encrypted via existing helper): a Bangalore address
    - Phone (encrypted): `9xxxxxxxxx` placeholder

  - Find-or-create initial `PatientVisit` (visit_type='initial', visit_date today, team_members).
  - Upsert all 8 baseline assessment rows on that visit using the existing `upsert()` helper pattern from `seed_faisal_test.py`. Clinical content: realistic palliative-oncology presentation (different from Faisal — e.g., metastatic prostate cancer with bone pain) so the two test patients are distinguishable.
  - Do **not** write `PatientAiSummary`. That's tested via the UI.

## Test plan

1. **Backend unit**: prompt builder with empty data → `Insufficient data recorded` per block; with full data → three non-empty blocks.
2. **Seed**: run `python backend/seed_test_patient.py` on a clean DB; re-run; row counts unchanged.
3. **End-to-end via UI**:
   - Open the seeded test patient.
   - Click Generate → confirm three narrative blocks populate, demographics/scores show without AI.
   - Edit nursing block → click Generate → confirm dialog appears.
   - Save → reload → blocks persist.
   - Download PDF → layout matches the card.
4. **Regression**: existing patients with old paragraph-only `summary_text` still render (fallback: show `summary_text` in a single legacy block if `summary_blocks` is NULL, until next Generate).
