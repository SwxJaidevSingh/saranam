## 2 · Architectural decisions to settle BEFORE coding

These three choices affect every downstream task. Lock them first.

### 2.1 Consultation model — **separate read-view, no new write table**

The meeting defined a consultation as the per-staff-member interaction:
- 1 home visit with 3 team members → **3 consultations**
- 1 outbound call from office → **1 consultation**
- 1 inbound call from caregiver → **1 consultation**

We already have three sources of truth on `feat/saranam-team`:

| Source | Path | What it stores |
|---|---|---|
| `patient_visit` | `backend/app/saranam/models/patient_visit.py` | In-person visits (home / OPD / IPD) + already has `team_members` JSONB array of roles |
| `call_logs` | `backend/app/call_logs/` | Voice calls via Twilio/Exotel (master number routing). Already on the branch. |
| `teleconsult` | `backend/app/teleconsult/` (from `a94d95a`, `0e84ce6`, `0278795`) | Scheduled video + voice sessions (Google Meet / EnableX) |

**Decision:** do **NOT** introduce a new `consultations` table. Build a read-side abstraction in `analytics/services.py` that UNIONs the three sources into a virtual "consultation event" stream. Cheaper, no migration, and each source keeps its lifecycle.

Counting rule for "Total Consultations":
```
total_consultations =
    SUM(len(visit.team_members)) for visit in patient_visit_completed
  + COUNT(call_logs WHERE direction IN (inbound, outbound) AND linked_patient IS NOT NULL)
  + COUNT(teleconsult_sessions WHERE status='completed')
```

Counting rule for "by modality":
- `in_person` = `patient_visit` rows excluding `visit_location='phone'`, counted as sum of team_members
- `inbound_call` = `call_logs WHERE direction='inbound' AND linked_patient IS NOT NULL`
- `outbound_call` = `call_logs WHERE direction='outbound' AND linked_patient IS NOT NULL`
- `video` (teleconsult video) — keep as its own bucket OR fold into outbound_call. **Decision needed (see §10 Q1).**

### 2.2 Home-care-day calendar — config-driven

Farzan: "4 home care days per week, 8 home-care days = 2 weeks."

**Decision:** introduce a backend setting `SARANAM_HOMECARE_WEEKDAYS` (default `[0,1,2,3]` for Mon–Thu, ISO weekday numbers). Helper `count_homecare_days_between(start_date, end_date)` iterates days and counts matches. All "X home-care days" metrics use this helper.

Dr. Ashwini to confirm the actual 4 days (see §10 Q2).

### 2.3 Delay reasons for late first visits — ship v1 without reasons

Farzan asked for "reasons for missing the target". Two paths:

| Option | Effort | When |
|---|---|---|
| v1: count-only ("X within target, Y missed") | Small | Now |
| v2: add `first_visit_delay_reason` enum + UI dropdown on the visit-completion form for late visits | Medium | Next milestone |

**Decision:** v1 in this scope; v2 in the next round once we know which dropdown values clinicians actually use in practice.

## 7 · Migration / backfill

Two backfill jobs, both idempotent, both run once:

### 7.1 Classify legacy `phone` visits

```sql
-- Map old patient_visit rows with visit_location='phone' into call_logs equivalents
-- so historical analytics show consistent modality breakdown.
-- Heuristic: if visit notes contain 'caregiver called' / 'patient called' → inbound,
-- else default to outbound (matches the team's typical pattern).
```

Ship as a Python script under `backend/scripts/backfill_phone_visits.py`. Dry-run mode first, then `--apply`. Log every classification with the reasoning string used.

### 7.2 First-visit cache (optional optimisation)

The `/donor/registration-to-first-visit` query computes `MIN(visit_date)` per patient on every request. For ~thousands of patients this is fine. If it gets slow, add a materialised `patient.first_visit_date` column populated by a trigger + one-time backfill. **Don't pre-optimise — measure first.**
