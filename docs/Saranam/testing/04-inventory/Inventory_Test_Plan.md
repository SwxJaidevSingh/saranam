# Saranam India Health Care — Inventory Module Manual Test Plan

**Module:** Inventory (`INV`)  
**Production URL:** https://saranam.fieldintel.ai  
**Version:** 1.0  
**Date:** 2026-06-01  
**Prepared by:** QA Engineering (Manual)  

## Purpose & How to Use

This is the GO-LIVE manual regression pack for the **Inventory** module of the Saranam India Health Care platform (React frontend + FastAPI/Flask backend). It is intended to be executed **manually in a browser** by the testing team, recording **Pass/Fail** for each case in Excel.

How to use:

1. Complete the **Test Data / Preconditions** (Section 5) before starting.
2. Execute cases in ID order per section; follow the numbered **Steps** exactly with the given **Test Data**.
3. Compare observed behaviour against **Expected Result**. Keep browser **DevTools (Network + Console)** open to confirm the **API** column (method + path, status codes, payloads).
4. Record the outcome in **Actual Result**, set **Status** (Pass/Fail/Blocked), and capture defect IDs/screenshots in **Remarks**.
5. Cases tagged **DEFECT-WATCH** in the Expected Result describe a code-level mismatch found during analysis — pay special attention and raise a defect if the behaviour is confirmed.

The pack contains **120** test cases across the Inventory sub-areas.

## 1. Scope

### In Scope

- Inventory Dashboard KPIs, quick actions, module cards, refresh, loading/empty states
- Medicines Master: list, search, pagination, add/edit/deactivate medicine, all form fields and validation
- Stock Management: stock list, location filter, status filter, pagination, stock-level bar, value, category, status chips
- Purchase Orders: list, status filter, client-side search, pagination, 3-step creation wizard, PO detail, submit/approve/receive/print, goods receipt with batch details
- Dispensing: records list with type/date filters and search, 4-step dispensing wizard (patient/prescription/batch/review), dispensing dashboard KPIs, dispensing detail with medicine return
- Alerts: alert list with type/severity/status tabs, acknowledge, resolve, bulk acknowledge, alerts dashboard with breakdown
- Provider Stock: provider locations list, setup provider, assign stock, return stock, expand provider to view stock
- Cross-cutting selectors: SupplierSelector, LocationSelector, PatientSelector, PrescriptionSelector, QuickDispenseSelector, BatchSelector (FIFO/FEFO)
- Role-based access (admin/data_entry/viewer), 401 session handling, non-existent ids
- API request/response/error verification for all inventory endpoints used by the UI

### Out of Scope

- Requisitions module (no UI route wired in App.jsx; backend endpoints exist but are not exercised by the Inventory screens)
- Analytics deep reports (ABC-VED, consumption, turnover) beyond the dashboard/KPI consumption already wired to UI
- Stock-movements list screen (no dedicated route in App.jsx)
- Immediate-dispense endpoints (consumed by Saranam visit flow, not by the Inventory screens under test)
- Suppliers CRUD screen and Locations CRUD screen (no dedicated routes; only consumed via selectors)
- Login/authentication module internals (covered by the Auth test pack); only session expiry behaviour is verified here
- Backend database performance/load testing

## 3. Roles & Access

All Inventory routes require an authenticated session (JWT access_token in localStorage; Authorization: Bearer header added by the axios client). Backend RBAC (role_required decorator) maps roles to permissions: admin = {read, write, approve, dispense, manage}; data_entry = {read, write, dispense}; viewer = {read}. Read endpoints (lists, dashboards, detail GETs) need 'read'. Create/edit medicine, create/update/submit PO, create supplier, transfer stock, acknowledge/resolve alerts, provider-stock assign/return/setup need 'write'. Delete medicine, delete location/supplier, manual stock update (/stock/update), generate alerts need 'manage'. Approve/cancel PO and approve/reject requisition need 'approve'. Dispense and return-dispensed need 'dispense'. Missing/invalid token returns 401 (client attempts refresh then redirects to /login). A logged-in user lacking the required permission receives HTTP 403 with message 'Insufficient permissions. Required: ...'. Unknown user id on a valid token returns 401 'User not found'.

| Role | Permissions | Example allowed | Example denied (403) |
|------|-------------|-----------------|----------------------|
| admin | read, write, approve, dispense, manage | Everything | — |
| data_entry | read, write, dispense | Create/edit medicine, create PO, dispense | Approve/cancel PO, delete medicine, manual stock update, generate alerts |
| viewer | read | View lists/dashboards/details | Create/edit/delete, dispense, approve, manage |

## 4. API Endpoints

Base URL: `${VITE_API_URL}` (default `http://localhost:5000/api`; production resolves under the app domain). Auth: `Authorization: Bearer <access_token>`. A 401 triggers a single refresh attempt then redirect to `/login`.

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/api/inventory/medicines` | List medicines with page, per_page, search, category, essential, is_active; returns {medicines,total,page,per_page,pages} |
| GET | `/api/inventory/medicines/{id}` | Get a single medicine by id (404 if not found) |
| GET | `/api/inventory/medicines/search` | Type-ahead search medicines by q (limit max 100) |
| POST | `/api/inventory/medicines` | Create medicine (write); 201 success, 422 validation, 400 ValueError (e.g. duplicate) |
| PUT | `/api/inventory/medicines/{id}` | Update medicine (write); 422 validation, 404 if not found |
| DELETE | `/api/inventory/medicines/{id}` | Deactivate medicine (manage); 404 if not found |
| GET | `/api/inventory/locations` | List inventory locations (filter type, is_active) |
| GET | `/api/inventory/stock` | List stock levels (location_id, medicine_id, status, low_stock) - returns a flat array |
| GET | `/api/inventory/stock/low-stock` | List low-stock items |
| POST | `/api/inventory/stock/update` | Manual stock update (manage); StockUpdateSchema requires medicine_id, location_id, quantity>=0 |
| POST | `/api/inventory/stock/transfer` | Transfer stock between locations (write); 201 success, 400 ValueError |
| GET | `/api/inventory/suppliers` | List suppliers (page, per_page, is_active); returns {suppliers,total,...} |
| GET | `/api/inventory/batches` | List batches (medicine_id, location_id, status, expiring_soon); BatchSelector reads response.data.batches |
| GET | `/api/inventory/batches/expiring` | List batches expiring within ?days (default 30) |
| GET | `/api/inventory/purchase-orders` | List POs (page, per_page, status, supplier_id); returns {purchase_orders,total,page,per_page,pages} |
| GET | `/api/inventory/purchase-orders/{id}` | Get PO detail (404 if not found) |
| POST | `/api/inventory/purchase-orders` | Create PO (write); PurchaseOrderCreateSchema requires supplier_id + items[>=1] each {medicine_id, ordered_quantity>0, unit_price>=0}; 422 validation |
| PUT | `/api/inventory/purchase-orders/{id}` | Update a draft PO (write) |
| POST | `/api/inventory/purchase-orders/{id}/submit` | Submit PO for approval (write) |
| POST | `/api/inventory/purchase-orders/{id}/approve` | Approve PO (approve permission) |
| POST | `/api/inventory/purchase-orders/{id}/receive` | Record goods receipt (write); GoodsReceiveSchema expects {received_items:[{item_id, received_quantity>0, batch_number, manufacture_date, expiry_date>mfg, mrp?}]} |
| POST | `/api/inventory/purchase-orders/{id}/cancel` | Cancel PO (approve); body {reason} |
| GET | `/api/inventory/prescriptions/patient/{patient_id}` | Aggregate patient prescriptions from OPD + Saranam plan-of-care (UUID patient_id); 500 on error |
| GET | `/api/inventory/dispensing` | List dispensing records (page, per_page, patient_id, medicine_id); returns {dispensing_records,total,page,per_page,pages} |
| POST | `/api/inventory/dispensing/dispense` | Process dispensing (dispense permission); DispenseCreateSchema requires patient_id, medicine_id, dispensed_quantity>0, dispensed_from_location |
| POST | `/api/inventory/dispensing/validate-prescription` | Validate prescription (dispense) |
| GET | `/api/inventory/dispensing/check-availability` | Check availability (read); requires medicine_id, location_id, quantity>0 else 400 |
| GET | `/api/inventory/dispensing/{id}` | Get dispensing record by id (404 if not found) |
| POST | `/api/inventory/dispensing/{id}/return` | Return dispensed medicine (dispense); body {item_id, return_quantity, reason} |
| GET | `/api/inventory/dispensing/history/{patient_id}` | Get a patient's dispensing history |
| GET | `/api/inventory/alerts` | List stock alerts (type, status default active, severity); returns array (UI reads response.data.alerts) |
| POST | `/api/inventory/alerts/generate` | Run all alert checks (manage) |
| POST | `/api/inventory/alerts/{id}/acknowledge` | Acknowledge alert (write); 404 if not found |
| POST | `/api/inventory/alerts/{id}/resolve` | Resolve alert (write); body {notes/resolution_notes}; 404 if not found |
| GET | `/api/inventory/analytics/kpis` | Inventory turnover/KPIs (read); used by Dispensing Dashboard stat cards |
| GET | `/api/inventory/analytics/stock-summary` | Dashboard stats (read) |
| GET | `/api/inventory/provider-stock/locations` | List provider stock locations with summary (read) |
| GET | `/api/inventory/provider-stock/{provider_id}` | Get a provider's stock items (read) |
| POST | `/api/inventory/provider-stock/{provider_id}/setup` | Create a provider stock location (write); 400 ValueError |
| POST | `/api/inventory/provider-stock/{provider_id}/assign` | Assign stock to provider (write); backend reads medicine_id, quantity, from_location_id (KeyError -> 400) |
| POST | `/api/inventory/provider-stock/{provider_id}/return` | Return stock from provider (write); backend reads medicine_id, quantity, to_location_id (KeyError -> 400) |

Common response codes: **200/201** success, **400** business-rule/ValueError, **403** insufficient role permission, **404** not found, **422** schema validation error, **401** missing/expired token, **500** server error.

## 5. Test Data & Preconditions

- At least 3 user accounts mapped to backend roles: an 'admin' (all permissions), a 'data_entry' user (read+write+dispense, NO approve/manage), and a 'viewer' user (read-only). Confirm each can log in to https://saranam.fieldintel.ai.
- Master medicines seeded, e.g. Paracetamol 500mg Tablet (generic Acetaminophen, brand Crocin, GST 12%, HSN 30049099), Amoxicillin 500mg Capsule, Morphine 10mg Injection (Schedule X / narcotic), ORS Sachet. Note one medicine name for duplicate testing.
- At least 2 active inventory locations of non-provider type, e.g. 'Central Store' (central_store) and 'Saranam Pharmacy' (pharmacy), each with stock on hand.
- At least 2 active suppliers, one flagged preferred with a rating and delivery_lead_days, e.g. 'MedPlus Distributors' and 'Apollo Pharmacy Supplies', GST/PAN populated.
- Stock with batches across statuses: an OPTIMAL item, a LOW item, a CRITICAL/out-of-stock item, an OVERSTOCKED item; batches with varying expiry: one expired (past), one near-expiry (<30 days, e.g. 2026-06-20), one mid (<90 days), one healthy (>90 days). Use realistic batch numbers e.g. BATCH-PCM-2401, AMX-2403, MOR-2312.
- At least one PO in each status: draft, pending_approval, approved, partial_received, received, cancelled (create as needed). Capture their ids and po_number values.
- A Saranam/OPD patient with at least one active prescription / plan-of-care containing medications with pending quantities (for the prescription dispensing path), plus a patient with NO prescriptions (empty-state path). Capture patient ids (UUID).
- At least one existing dispensing record (with at least one returnable item) to exercise the detail/return flow; capture its id.
- At least one active alert per type if possible (low_stock, out_of_stock, near_expiry, expired) in active/acknowledged/resolved states; otherwise run POST /alerts/generate as admin to populate.
- At least one provider already set up under Provider Stock with some assigned stock, plus a valid provider UUID to use for the 'Setup New Provider' flow.
- Browser DevTools (Network + Console) available for API verification; a spare invalid/expired token to simulate 401.

## 7. Severity Legend & Sign-off

### Defect Severity

| Severity | Definition |
|----------|------------|
| **Critical (S1)** | Core inventory function broken or data corruption: cannot dispense, PO receipt fails, stock counts wrong, security/permission bypass, data loss. Blocks go-live. |
| **High (S2)** | Major feature fails with no reasonable workaround (e.g. PO create/approve fails, alerts cannot be acknowledged, wrong stock math). |
| **Medium (S3)** | Feature works but with a defect having a workaround (e.g. client-side-only search, count badge inaccuracies, stuck loading button). |
| **Low (S4)** | Cosmetic/UX or minor edge case with negligible business impact (labels, formatting, empty-state copy). |

### Priority

| Priority | Meaning |
|----------|---------|
| High | Must pass before go-live. |
| Medium | Should pass; schedule a fix if failing. |
| Low | Nice to have; track for later. |
