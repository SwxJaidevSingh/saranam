## Purpose & How To Use

This is the GO-LIVE manual test pack for the **Users** module (admin-only user management). Execute each case in a browser, observe the actual behaviour, and record the outcome directly in the Test Cases table: fill **Actual Result**, set **Status** (Pass / Fail / Blocked / N/A), and add any **Remarks** (defect ID, screenshot reference, environment note). Keep DevTools > Network open so you can verify the HTTP method, path, request payload and status code listed in the **API** column. Run permission/access cases (USR-001 to USR-007) first to confirm the role harness, then proceed top-to-bottom. The JSON source of truth for this plan is `users_test_cases.json` in this same folder.

## 1. Scope

### In Scope
- Users list screen at /users (load, loading skeleton, empty state, error alert, row display)
- Client-side search (name/email) and status filter (all/pending/active/inactive)
- Pending-approval badge and count behaviour
- Approve pending user (POST /users/{id}/approve)
- Reject pending user with confirm prompt (POST /users/{id}/reject)
- Activate / Deactivate approved user (PUT /users/{id}/toggle-status)
- Edit User modal: full_name, email, role; save/cancel/close; validation; success/error
- Role & permission integrity (role change alters access; deactivated/unapproved cannot log in)
- Access control: admin only; non-admin blocked/redirected; sidebar item hidden
- API request/response, status codes, 401/403 handling, error mapping
- Data integrity of is_active / is_approved flags after each action

### Out of Scope
- Admin-initiated user creation from /users (no Create/Add UI exists in this build)
- Phone / +91 mobile number capture (no phone field exists in the User model or any user form)
- Hard delete of users (no delete endpoint exists; only soft-delete via reject / deactivate)
- Password reset / change password from the Users screen (no such control exists here)
- Temporary-password generation (not implemented)
- Server-side pagination/role-filter exercised from the UI (UI fetches all users and filters client-side)
- Public self-registration flow at /register (covered by the Auth module test pack), tested here only as the user-creation precondition
- API key / service-account management

## 3. Roles & Access

Roles defined in backend Enum 'user_role' (app/common/models.py) and validated in schemas: admin, data_entry, viewer (exactly three; no doctor/nurse roles exist). Permission map (identical in backend User.has_permission and frontend AuthContext.hasPermission): admin = [create_form, edit_form, delete_form, view_form, submit_form, view_submission, view_analytics, manage_users]; data_entry = [view_form, submit_form, view_submission]; viewer = [view_form, view_submission, view_analytics]. Only 'admin' holds 'manage_users'. ACCESS to Users: (1) /users route is wrapped in ProtectedRoute requiredRole='admin' -> non-admins see an 'Access Denied' panel; unauthenticated users are redirected to /login. (2) The sidebar 'Users' nav item has permission:'manage_users' and is filtered out for non-admins. (3) Every backend Users endpoint uses @require_permission('manage_users') -> non-admin tokens get HTTP 403 {error:'insufficient_permissions'}; missing/expired tokens get HTTP 401. User account state gates login: register sets is_approved=False (pending); login is blocked with a specific message if is_approved=False ('pending admin approval') or is_active=False ('account deactivated').

### Role → Permission Matrix (from backend `User.has_permission` and frontend `AuthContext.hasPermission`)

| Permission | admin | data_entry | viewer |
|---|:--:|:--:|:--:|
| create_form | Yes | — | — |
| edit_form | Yes | — | — |

| view_form | Yes | Yes | Yes |
| submit_form | Yes | Yes | — |

> Only **admin** holds `manage_users`, which gates the entire Users module (route, sidebar item, and every API endpoint).

## 4. API Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/users` | List users. Query params role, status(active\|inactive), approval(approved\|pending\|rejected), search, page(default 1), per_page(default 50, capped 100). Returns {users,total,page,per_page,message}. NOTE: frontend usersApi.getAllUsers() sends no params; filtering/search is done client-side. Requires manage_users. |
| GET | `/api/users/{user_id}` | Get single user by UUID. 200 {user,message} or 404 {error:'user_not_found'}. (No UI caller in UsersList; API-level only.) Requires manage_users. |
| POST | `/api/users/{user_id}/approve` | Approve a pending user -> is_approved=True, is_active=True. 200 {user,message}; 400 {error:'approve_failed'} (e.g. already approved). Requires manage_users. |
| POST | `/api/users/{user_id}/reject` | Reject/soft-delete a user -> is_approved=False, is_active=False. 200 {user,message}; 400 {error:'reject_failed'}. Requires manage_users. |
| PUT | `/api/users/{user_id}` | Update full_name (>=2 chars), email (valid + unique), role (admin\|data_entry\|viewer). Validated by UpdateUserSchema (marshmallow). 200 {user,message}; 400 validation/{error:'update_failed'} incl. 'Email already in use'/'Invalid role'. Requires manage_users. |
| PUT | `/api/users/{user_id}/toggle-status` | Flip is_active (Activate<->Deactivate). 200 {user,message}; 400 {error:'toggle_failed'}. Requires manage_users. |
| GET | `/api/users/pending/count` | Count of users with is_approved=False AND is_active=True. 200 {count}. Requires manage_users. |
| POST | `/api/auth/register` | Self-registration (user-creation precondition). Body email,password(>=8),full_name(>=2),role(default viewer). Creates user is_approved=False. 201 {user,message}; 400 duplicate/validation. Public (no auth). |
| POST | `/api/auth/login` | Login for re-auth / verifying blocked users. 200 with tokens; 401 'Invalid credentials' / 'pending admin approval' / 'account deactivated'. |

## 7. Severity Legend & Sign-off

### Severity Legend

| Severity | Meaning |
|---|---|
| Critical | Security/access-control breach, data loss/corruption, or module unusable (e.g. non-admin can manage users, sensitive field leaked, last admin lockable out). |
| High | Core function broken or wrong result (approve/reject/edit/toggle fails or mis-updates; role change does not change access). |
| Medium | Function works but with incorrect validation, error handling, or filter/count inconsistency. |
| Low | Cosmetic / UI / minor copy or badge-colour issue, no functional impact. |

### Status Values

`Pass` — behaves as expected | `Fail` — defect found (log severity + ticket) | `Blocked` — cannot execute (dependency/env) | `N/A` — not applicable to this build.
