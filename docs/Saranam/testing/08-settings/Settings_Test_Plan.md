## Purpose & How To Use

This document is the GO-LIVE manual test pack for the **Settings** module (route `/settings`). Execute every case below in a browser against the production (or final staging) build, then record the outcome in the **Actual Result**, **Status** (Pass/Fail/Blocked) and **Remarks** columns (left blank for the tester). Work top to bottom within each section; complete the **Test Data / Preconditions** in Section 5 before starting. Log every failure as a defect using the severity legend in Section 7. The machine-readable copy of these cases lives alongside this file at `settings_test_cases.json`.

> **IMPORTANT — what the Settings page actually is.** After reading the source (`frontend/src/pages/Settings.jsx` + `frontend/src/context/ThemeContext.jsx`), the `/settings` page is a **purely client-side Appearance & Preferences screen**. It has **exactly five sections** — Appearance (Dark Mode), Typography, Border Radius, Density and Accessibility (Reduce Motion + High Contrast) — all persisted to the browser's `localStorage` under the key **`themeConfig`** via `ThemeContext`. The page makes **NO API calls** and has **NO profile editing, NO change-password form, NO notification preferences, NO organization settings and NO logout button**. Those areas are listed in **Out of Scope** as *NOT IMPLEMENTED* so the test team knows they are intentionally absent (there is not even a change-password endpoint in `backend/app/auth/routes.py`).

Scope at a glance: **33 test cases** across 18 functional areas, covering 1 screen and 0 page-owned API endpoints (3 indirect auth endpoints bound the session).

## 1. Scope

### In Scope
- Page load: `/settings` renders header (title 'Settings' + subtitle) and all five preference Cards (Appearance, Typography, Border Radius, Density, Accessibility) without errors
- Appearance section: Dark Mode Switch toggle (on=dark / off=light), live theme application app-wide (`document.documentElement` `dark` class), icon/label text changes (Moon/Sun, 'Dark theme is enabled' / 'Light theme is enabled'), 'Current theme' read-out, system-preference note shown only when no preference stored
- Typography section: three font option buttons (Inter, System Default, Open Sans), selected-state highlight (primary border), live font-family application to document root, Google Fonts stylesheet injection for Inter / Open Sans
- Border Radius section: four buttons (none/small/medium/large), selected-state highlight, live `data-border-radius` attribute + preview swatch radius
- Density section: three buttons (compact/comfortable/spacious), selected-state highlight, live `data-density` attribute
- Accessibility section: Reduce Motion Switch (adds/removes `reduce-motion` class), High Contrast Switch (adds/removes `high-contrast` class)
- Persistence: all preferences saved to `localStorage` `themeConfig` immediately on change and restored on reload, on navigation away and back, and in a new tab of the same browser profile
- Data integrity: a single `themeConfig` JSON object holds all six keys (theme, font, borderRadius, density, reducedMotion, highContrast); changing one preference must not reset the others; corrupted/partial JSON falls back to / merges onto defaults
- System theme detection: default theme follows OS `prefers-color-scheme` on a fresh profile; once a preference is stored, OS theme changes no longer auto-switch
- App-wide effect verification: dark mode / font / radius / density applied to other screens (Dashboard, Patients), proving these are global document-level styles
- Accessibility / keyboard: labels associated with switches (`htmlFor`), switches & option buttons keyboard-focusable and operable (Tab/Space/Enter)
- Route guard & session: `/settings` requires an authenticated session (any role, permission=null); unauthenticated access redirects to `/login`; expired-token 401 triggers refresh-and-retry then `/login` on refresh failure

### Out of Scope
- Profile view/edit (name, email, phone, +91) — **NOT IMPLEMENTED** on the Settings page; there is no profile form or save button in `Settings.jsx`
- Change Password (current/new/confirm) — **NOT IMPLEMENTED**; no password fields and no change-password endpoint exists in `backend/app/auth/routes.py`
- Notification preferences — **NOT IMPLEMENTED** on the Settings page
- Organization / system settings — **NOT IMPLEMENTED** on the Settings page
- Logout from Settings — **NOT IMPLEMENTED** on the Settings page (logout lives in the layout/header, covered by the Auth module)
- Server-side persistence of preferences — preferences are `localStorage`-only; not saved to the backend and not synced across devices/browsers (verifying this absence is in scope as data-integrity notes; building/altering server sync is out of scope)
- Saranam Scheduling Settings page (`/saranam/scheduling/settings`) and IPD Form Configuration — separate modules, not the `/settings` appearance page
- Pixel-perfect visual design / exact colour values of themes (only that the theme visibly changes is in scope)
- Auth login screen internals (covered by the Auth/Users module; only redirect behaviour is referenced here)

## 3. Roles & Access

The `/settings` route is registered in `App.jsx` as a child of the `ProtectedRoute`-wrapped dashboard layout, and the sidebar nav entry carries `permission: null`. Any authenticated user (admin, data_entry or viewer) may open Settings — there is **no role or permission gate** beyond being logged in. `ProtectedRoute` behaviour: while `AuthContext` is loading it shows a 'Loading...' splash; if there is no user it redirects (`Navigate replace`) to `/login`. All preferences are stored only in the browser's `localStorage` (`themeConfig`) and are therefore **per-browser-profile and per-device**, not tied to the user account — logging in as a different user on the same browser inherits the same appearance settings, and the same user on a different device sees defaults. The page issues no API calls, but the surrounding session still matters: the axios client attaches the Bearer `access_token` to all requests, and on any background 401 it attempts a one-time refresh via `refresh_token` and, on failure, clears localStorage tokens and hard-redirects to `/login`.

## 4. API Endpoints

The Settings page itself makes **no API calls** — all preferences are read from / written to browser `localStorage`. The endpoints below only *bound the session* in which the page runs (called by `AuthContext`/the axios interceptor, not by Settings).

| Method | Path | Purpose |
| --- | --- | --- |
| N/A | N/A | Settings makes NO API calls. Preferences are read/written in `localStorage` (`themeConfig`) via `ThemeContext`; nothing is persisted server-side. |
| GET | `/api/auth/me` | Indirect only. Called once by `AuthContext` on app init to verify the stored token and populate the current user; on failure tokens are cleared. 200 `{user}` / 404 `user_not_found`. |
| POST | `/api/auth/refresh` | Indirect only. Triggered by the axios response interceptor on any 401 using `refresh_token`; on success stores a new `access_token` and retries, on failure clears tokens and redirects to `/login`. 200 `{access_token}` / 401 `refresh_failed`. |
| POST | `/api/auth/logout` | Indirect only. Not callable from Settings (no logout control here); logout is triggered from the layout/header. 200. Listed for completeness of the auth surface. |

## 5. Test Data / Preconditions

- A valid logged-in session for an **ADMIN** user (valid `access_token` + `refresh_token` + `user` in localStorage).
- A valid logged-in session for a **NON-ADMIN** user (data_entry or viewer) to confirm Settings is accessible to every role (no permission gate).
- Two browsers / profiles: one with **NO** `themeConfig` in localStorage (fresh) to test system-theme detection and the system-preference note; one with an existing `themeConfig` to test restoration.
- Ability to open browser DevTools to inspect localStorage key `themeConfig`, the `<html>` element classes (`dark`, `reduce-motion`, `high-contrast`), attributes (`data-border-radius`, `data-density`) and inline `style.fontFamily`, plus the Network tab to confirm zero requests on preference changes.
- Ability to change the OS / browser colour scheme to dark and to light (e.g. macOS System Settings > Appearance, or DevTools 'Emulate prefers-color-scheme') to test system detection.
- Ability to throttle / go offline to confirm the page and toggles still work with no network.
- Ability to expire or corrupt the `access_token` to exercise the 401 → refresh → `/login` path while Settings is the open page.
- Known starting appearance baseline before each persistence test: theme=light, font=inter, borderRadius=medium, density=comfortable, reducedMotion=false, highContrast=false.
- Realistic India context users for the role checks, e.g. admin `priya.menon@saranam.in`, nurse `lakshmi.devi@saranam.in` (used only to log in; Settings shows no user data).

## 7. Severity Legend & Sign-off

### Severity Legend
| Severity | Definition |
| --- | --- |
| **Critical** | Blocks go-live: page crashes/white-screens, preferences cannot be changed, or an unauthenticated user can reach Settings. |
| **High** | Major function broken: a preference does not apply app-wide, does not persist across reload, corrupted config crashes the app, or the route guard fails for a role. |
| **Medium** | Partial/secondary issue: a single preference persists wrong, system-detection misbehaves, or keyboard/label association is broken but mouse works. |
| **Low** | Cosmetic / minor: icon/label wording, duplicate font-link injection, offline font fallback, or minor highlight styling. |

### Status Values
`Pass` — behaves exactly as the Expected Result.  `Fail` — deviates from Expected Result (log a defect with severity).  `Blocked` — cannot execute (dependency/env/data missing).
